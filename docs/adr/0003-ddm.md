# ADR 0003: Add a bounded iPadOS device-channel DDM model

- Status: Accepted
- Date: 2026-10-09

## Decision

`mdm-core` exposes a dedicated `AppleDeclaration` value for the common Apple
DDM declaration shape:

```json
{
  "Type": "com.apple.activation.simple",
  "Identifier": "declaration-id",
  "ServerToken": "opaque-revision-token",
  "Payload": {}
}
```

The model is independent of HTTP, SQLite, APNs, and the DDM check-in/status
transport. The service layer owns declaration manifests, persistence,
authentication, device capability discovery, and response endpoints. The
device channel can request a DDM synchronization through
`CommandKind::DeclarativeManagement`; the existing enrollment profile does
not advertise DDM as a profile capability.

## Target boundary and Apple version metadata

Apple's public declaration schemas for the selected types are introduced in
iOS/iPadOS 15.0. That metadata is a schema availability statement shared by
several enrollment modes. This engine deliberately accepts an iPadOS
**device-channel target only from iPadOS 16.0** because its current enrollment
flow and runtime gate are limited to that device-enrollment boundary. The
distinction is represented in the core API by
`AppleDeclarationType::schema_minimum_ipados()` (15.0) and
`device_channel_minimum_ipados()` (16.0). It prevents a schema introduction
from being mistaken for a tested enrollment capability.

The current target is `DdmTarget::ipados_device`: iPadOS, device channel, and
the recorded OS version. User channel, macOS, tvOS, watchOS, visionOS, and
other enrollment modes are outside this release. The version check is a
minimum support check; it does not claim that every future device release is
fully tested.

The version distinction follows Apple's schema data at the pinned release
commit `09f249a06e7e3289930bf6d05f38fb562f748ebf` and Apple's enrollment
documentation:

- <https://github.com/apple/device-management/tree/09f249a06e7e3289930bf6d05f38fb562f748ebf/declarative/declarations>
- <https://github.com/apple/device-management/blob/09f249a06e7e3289930bf6d05f38fb562f748ebf/declarative/declarations/activations/simple.yaml>
- <https://github.com/apple/device-management/blob/09f249a06e7e3289930bf6d05f38fb562f748ebf/declarative/declarations/configurations/management.status-subscriptions.yaml>
- <https://github.com/apple/device-management/blob/09f249a06e7e3289930bf6d05f38fb562f748ebf/declarative/declarations/configurations/app.managed.yaml>
- <https://github.com/apple/device-management/blob/09f249a06e7e3289930bf6d05f38fb562f748ebf/declarative/declarations/management/server-capabilities.yaml>
- <https://support.apple.com/guide/deployment/review-declarative-configurations-depf858becef/web>

## Supported declaration types

This milestone validates the following Apple schema types:

| Type | Schema introduced | Engine device target | Payload validation |
| --- | --- | --- | --- |
| `com.apple.activation.simple` | iPadOS 15.0 | iPadOS 16.0+ device channel | `StandardConfigurations` is a non-empty array of unique identifiers; optional `Predicate` is a non-empty string |
| `com.apple.configuration.app.managed` | iPadOS 17.2 | iPadOS 17.2+ device channel | Exactly one of `AppStoreID`, `BundleID`, or HTTPS `ManifestURL`; App Store sources require `InstallBehavior.License.Assignment`; install behavior is limited to `Install` and `License` |
| `com.apple.configuration.management.status-subscriptions` | iPadOS 15.0 | iPadOS 16.0+ device channel | `StatusItems` is a non-empty array of objects with unique names from the engine allowlist |
| `com.apple.management.server-capabilities` | iPadOS 15.0 | iPadOS 16.0+ device channel | `Version` is a non-empty string and `SupportedFeatures` is a dictionary with opaque values |

The status-subscription allowlist currently contains the following official
status item names. The item-level schema introduction check is applied in
addition to the target gate:

| Status item | Schema introduced on iPadOS |
| --- | --- |
| `device.identifier.serial-number` | 16.0 |
| `device.identifier.udid` | 16.0 |
| `device.model.family` | 15.0 |
| `device.model.identifier` | 15.0 |
| `device.model.marketing-name` | 15.0 |
| `device.model.number` | 17.0 |
| `device.operating-system.build-version` | 15.0 |
| `device.operating-system.family` | 15.0 |
| `device.operating-system.marketing-name` | 15.0 |
| `device.operating-system.version` | 15.0 |
| `management.client-capabilities` | 15.0 |
| `management.declarations` | 15.0 |
| `app.managed.list` | 17.2 |

Unknown status item names are rejected when creating a subscription because
the service does not claim to configure them. Status reports received from a
device remain an opaque protocol boundary: the protocol accepts unknown
future status-item keys, stores their JSON values, and does not infer that a
declaration was applied from their presence.

Unknown declaration types, missing required keys, wrong JSON types, duplicate
identifiers, duplicate status items, and unknown payload keys are rejected.
`SupportedFeatures` follows Apple's schema as a dictionary of opaque feature
values; the engine does not invent a closed feature enum. The selected engine
endpoint exposes declaration identifiers as one path segment, so `/` is
rejected in `Identifier` and in activation standard-configuration references
even though Apple's general declaration schema treats those strings as
opaque.

## Identity and equality

`Identifier` and `ServerToken` are preserved as opaque strings. They must be
non-empty, free of control characters, and no longer than 64 UTF-8 bytes.
The implementation never parses, orders, or normalizes server tokens. A
revision match requires exact equality of declaration type, identifier, and
server token.

`canonical_content_json` recursively sorts JSON object keys and preserves array
order and scalar values. `content_equal` compares declaration type and
canonical payload, excluding identifier and server token. This lets
persistence detect the unsafe case where the same declaration identifier and
server token are reused with different content while treating JSON object
ordering as insignificant.

## Traditional profile ownership

The selected declarations do not manage profile settings. Their explicit
`ProfileConflictPolicy` is `TraditionalProfileUnaffected`, and their
`ProfileOwnership` is `Unclaimed`; a traditional MDM profile remains the
owner of its settings. This milestone does not implement the
`com.apple.configuration.legacy` bridge, profile structure matching, or
profile takeover. A future bridge must match the existing profile identity and
payload structure before transferring ownership.

## Delivery semantics

DDM synchronization can cause the device to apply configuration autonomously.
It is therefore represented by `CommandKind::DeclarativeManagement`, whose
response timeout becomes `OutcomeUnknown` rather than silently retrying. A
caller must reconcile the device status or explicitly cancel before issuing a
new state-changing DDM operation.

## Consequences

The core can validate and compare the selected declarations deterministically
without claiming support for every Apple schema or every Apple platform. A
status report can carry a future item without breaking ingestion, but that
does not add it to the declaration allowlist. Adding another declaration or
status item requires a deliberate schema, target support, and ownership
review, plus device acceptance evidence.
